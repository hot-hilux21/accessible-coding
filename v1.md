## 1. What exists today

### Runtime shape

Two deployment targets from one codebase:

| Target | Entry point | Host |
|---|---|---|
| Windows desktop `.exe` | `app.py` — runs Flask inside a PyWebView / WebView2 native window | user machine, offline |
| Browser web app | `wsgi.py` — WSGI callable | Render (`render.yaml`), Railway (`railway.json`), Vercel (`vercel.json`) |

`app.py` binds a free port, spawns the WSGI server as a subprocess, waits for it to answer,
then opens the native window. It only shuts the server down if it started that server itself
(`_is_our_server`, `_free_port`), so an already-running instance is not killed.

### Source layout (`src/accessible_ide/`)

- `routes.py` — all HTTP routes; the largest file. Contains the run endpoint, the config
  read/write endpoints, the update endpoints, the access-code gate, and the static/template wiring.
- `i18n.py` plus `i18n/*.json` — six locales: `en`, `es`, `fr`, `hi`, `ar`, `uk`.
- `glossary.py` — plain-English definitions of Python terms used by the error translator and the UI.
- `packages.py` — package-install helper for the in-app package manager.
- `shell.py`, `shell_bootstrap.py` — shell integration and startup wiring.
- `trace_runner.py` — trace execution used by the step-through / debugging view.
- `updater.py` — update check, download, and applying the update on exit.
- `utils/colour.py` — colour maths (contrast ratios, theme token derivation).
- `static/css/style.css` — the design tokens and every theme.
- `static/js/app.js`, `tint.js`, `active-line.js` — app behaviour and syntax-highlight tinting.
  `codemirror.min.js`, `python.min.js`, `matchbrackets.min.js` are vendored CodeMirror.
- `templates/index.html` — the single page.
- `assets/fonts/` — bundled `OpenDyslexic` and `Atkinson Hyperlegible`, plus `Lexend`, `Nunito`,
  `Almarai`, `Mukta`, each with its OFL licence text in `assets/fonts/licenses/`.
- `assets/icon.ico`, `installer/assets/wizard-image.png`, `installer/assets/wizard-small.png`.

### Features that work today

- CodeMirror editor restricted to Python, with bracket matching and active-line highlighting.
- Run endpoint with a 10-second timeout and a sandbox that rejects blocked imports, `open()`,
  and dunder attribute names.
- Error translation: Python tracebacks are rewritten into plain-English sentences, backed by
  `glossary.py`, with per-error unit tests.
- Focus mode: hide the gutter, or blur every line except the active one.
- Four themes, all contrast-checked by `tests/test_contrast.py`.
- Text-to-speech over the editor buffer.
- Config persistence through the config endpoints (fonts, themes, focus settings) — nothing
  about appearance is hardcoded.
- Optional access code on the hosted version, with a lockout after repeated failures.
- Rate limit of 10 runs per minute per caller.
- Update check, download, and apply-on-exit; the installer relaunches the app after an update
  as the original user (`ShouldRelaunch`, `runasoriginaluser` in `installer.iss`).
- Package manager for installing Python packages from the UI.

### Tests and tooling

- 701 tests across 20 test modules in `tests/`, including:
  - `test_contrast.py` — the WCAG arbiter; every shipped theme must pass.
  - `test_security.py` — the sandbox and the access-code/lockout paths.
  - `test_error_translation.py`, `test_glossary.py` — plain-English error output.
  - `test_i18n.py` — key parity across all six locale files.
  - `test_template_contract.py` — the page and the JS agree on element IDs.
  - `test_desktop_launch.py`, `test_web_detection.py` — the two runtime shapes.
  - `test_updater.py`, `test_update_api.py`, `test_version_stamp.py`, `test_packaging.py`.
  - `tests/dom_harness.js` — a small JS harness so DOM behaviour can be asserted from Python.
- `tools/check_publish.py` — refuses a version move backwards; `tools/stamp_version.py` — stamps
  the version into the built manifests.
- CI: `.github/workflows/build-exe.yml` (Windows binary) and `build-release.yml` (release and
  manifest). Both derive the version from `git describe --match 'v[0-9]*'` so beta tags cannot
  be mistaken for the stable line.

### MVP status against the requirements doc, section 10

The MVP checklist items are delivered: Python editor, running code, plain-English errors,
dyslexia-friendly fonts, focus and blur modes, themes, text-to-speech, local config storage,
browser plus Windows desktop builds, and a public open-source repository.

## 2. What is obviously missing versus the requirements doc

These are gaps between the document and the shipped v1.0.0, not opinions about polish.

1. **No packaging metadata.** There is no `pyproject.toml` and no `setup.py`. The version lives
   in three places — `installer.iss` (`MyAppVersion "1.0.0"`), `requirements.txt` pins, and the
   stamped build output — so there is no single source of truth for a Python version.
2. **No accessibility statement or audit record.** There is no `docs/accessibility.md` or
   equivalent. The repository describes the app as accessible without a recorded test of that
   claim (contrast tests cover colour only; they do not cover keyboard, screen-reader, or motion).
3. **No keyboard-only or screen-reader test coverage.** The suite is Python and DOM-level. There
   is no test that drives the page with only the keyboard, and no test of the ARIA surface.
4. **No user documentation.** `docs/` holds `.gitkeep` and `docs/code-signing.md` only. There is
   no install guide, no feature guide, and no guide for a dyslexic learner or a teacher.
5. **No code signing.** `docs/code-signing.md` describes the intent, but the shipped installer is
   unsigned, so Windows SmartScreen warns on every install.
6. **No multi-file or multi-tab editing.** The editor is a single buffer; the requirements doc
   treats project-style work as future scope, and that future scope is not started.
7. **No i18n coverage test for the prose.** Key parity is tested, but the six locales were not
   reviewed by a speaker; `ar` is present while the UI does not appear to be RTL-aware.
8. **No TTS engine matrix test.** The requirements doc lists ReciteMe, pyttsx3, eSpeak-ng, and
   Coqui as candidates. There is a TTS path in the app but no test pinning which engine is used
   or what happens when none is installed.
9. **No crash reporting or local error log.** When the desktop app fails before the window opens
   there is nothing on disk to read.
10. **No licence decision recorded in-repo beyond `LICENSE`.** `AGENTS.md` says MIT/GPL/Apache 2.0
    is open, and `LICENSE` picks one; the choice is not restated in the README, and the bundled
    fonts' OFL notices are in `assets/fonts/licenses/` but not surfaced to the user.

## 3. Questions worth answering in the audit

- Does the sandbox in `routes.py` hold up against a determined Python author, or is it a
  convenience guard rather than a security boundary?
- Is the access-code lockout in `routes.py` safe against timing analysis and against a restart,
  given it is in-memory?
- Does `tests/test_contrast.py` measure every foreground/background pair the UI can produce, or
  only the theme table in `routes.py`?
- Does focus mode's blur respect `prefers-reduced-motion` and does it ever blur an error message?
- Is `prefers-reduced-motion` honoured anywhere in `style.css` or `app.js`?
- Can the whole flow — open, type, run, read an error, switch theme, turn on TTS — be completed
  with the keyboard alone?
- What does the page announce to a screen reader when a run finishes or an error appears?
- Are the six locale files complete in the sense a reader would care about, or only in keys?
- Does the update flow verify the downloaded installer against the published hash before running it?
